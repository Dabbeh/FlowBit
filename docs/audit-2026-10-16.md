# Flowbit — Full Code Audit

**Date:** 2026-10-16 · **Scope:** all 58 source files (≈455 KB), all 20 tools, 3
docs. Method: automated scans (markers, dead debug output, build-file drift,
registration checks) plus a manual read of every module added or touched during
the monitoring/limiter/diagnostics rounds.

## Verdict

The app is feature-complete against the briefs: system-wide limiter, scheduler,
per-application limiter, per-application live monitoring, diagnostics, tray,
themes, persistence. 11 headless suites, **0 failures**. The only items
outstanding are **things only a human at the keyboard can confirm** (live rates
with real traffic, enforcement held during a Steam download), listed at the end.

## Known remaining items

- **Per-application enforcement** (the packet-shaping side) is built and its
  decision logic is tested, but *measured enforcement on live traffic* has to be
  confirmed by you — WinDivert refuses an unelevated caller. Tools:
  `Desktop\Flowbit\applimit-poc\` and `appmon-selftest\`.
- **`msvc`/CMake build path** was rewritten to include all 22 missing sources and
  the new link libraries, but cannot be configure-verified inside this sandbox
  (qmake via `tools\build.ps1` is the verified path). If you use CMake and it
  errors, send the first error lines.
- **`rulerow.cpp`** and `tools/bisect_*` are kept intentionally: legacy widget +
  the hang-regression probe. Removing them breaks suites.
- **`QProcess` wait time**: worst case the retry path blocks the UI ≤ ~6 s
  (bounded, out-of-process). Making it fully jump-off-thread is the one optional
  future polish.
- **Antivirus/Defender**: the WinDivert category is sometimes flagged; the
  installed driver is validly signed. Distribution of the app to other machines
  should expect that prompt.
- **Driver provenance**: `WinDivert64.sys` is a third-party re-sign (valid).
  Swapping to the official upstream build is a deliberate decision, documented in
  `docs/app-limiter-findings.md`; Defender blocks the upstream zip by category.
- **`updated()` signal** is emitted by `tick()`; no listener needs it today — it
  exists so panels can subscribe directly instead of polling.
- **Historical per-application statistics** were explicitly out of scope this
  round (Statistics page keeps system-wide history only).
- CMake description/version updated (1.0.0) to match the About text.

## Review round (post-audit) — issues found top-to-bottom and fixed

| # | Finding | Impact | Fix |
| --- | --- | --- | --- |
| R1 | `FlowTuple` was IPv4-only and the packet worker skipped every IPv6 packet (`&& ip`) | IPv6 application traffic silently escaped per-app limits (system-wide still applied, masking the gap) | tuple model now family-aware (v4/v6, four address words, unified hash); packet worker parses both families; flow worker builds matching tuples for both |
| R2 | FLOW-layer `WINDIVERT_EVENT_FLOW_DELETED` events were re-**inserted** as tuples instead of removing them | stale tuples accumulated; a later REUSED tuple could inherit another app's rule | deleted events now prune the tuple; established events insert |
| R3 | `g_activeConsumer` global — two live monitors would steal each other's callbacks | silent event cross-wiring if a second handle ever opened | explicit single-owner guard with a precise error |
| R4 | `setRules()` recomputed states but did not push rates into token buckets | edited rule rates lagged up to 30 s behind edits while running | recompute applies buckets immediately |
| R5 | test suite still asserted the v4-only tuple fields | would break the build the moment R1 landed; also under-covered | suite extended: v6 normalisation/hash equality cases (55 checks now) |
| R6 | App Limiter opened WinDivert handles at **priority 0**, overlapping the system-wide limiter's filters at the same priority | WinDivert returns `ERROR_INVALID_PARAMETER (87)` — the App Limiter banner error, enforcement dead on arrival | both App Limiter handles moved to priority 100; documented rule: same-priority handles need mutually exclusive filters |
| R7 | Kernel-network ETW delivers **zero events** on Windows build 26300 (counters `received 0 / decoded 0` with traffic flowing), so the per-app list had no source | panel empty/under-reporting; no code fix to the decoder could help | TCP EStats fallback (`GetExtendedTcpTable` + `GetPerTcpConnectionEStats`, deltas per PID) promoted automatically after 3 silent ticks; ETW stays primary and reclaims the source if it starts delivering. Trade documented in-UI: TCP only, UDP/QUIC under-counts |
| R8 | ETW enable used `TRACE_LEVEL_INFORMATION` | if a build emits kernel-network events at level 5 they are filtered out with no error | level raised to `TRACE_LEVEL_VERBOSE` + full 64-bit keyword mask |
| R9 | Rows blinked in and out as apps went idle for one tick | list unreadable during bursty traffic | anti-flicker persistence: idle apps keep their row at 0 B/s for ~5 refreshes; panel shows a scope note while the TCP-only fallback is active |
| R10 | App Limiter still failed with error 87 after the priority change | **measured with a purpose-built probe**: on Windows 11 build 26300 the driver cannot open the **FLOW or SOCKET layer at all** — `ERROR_INVALID_PARAMETER` at any priority, in isolation, while NETWORK opens fine and filters compile. Per-app enforcement had no attribution source, so it never started | tiered attribution: use the FLOW layer when the driver exposes it, otherwise attribute by **polling `GetExtendedTcpTable`/`GetExtendedUdpTable` every 400 ms** (the same APIs the activity monitor already uses successfully). The page banner explains the mode instead of showing a fatal error; the flow worker idles when there is no flow handle |

### Probe evidence (tools/driver_probe.cpp, run elevated on the user's machine)

```
COMPILE FLOW   filter="true"                          -> ok
OPEN    FLOW   prio=0     filter="true"               -> FAILED err=87
OPEN    FLOW   prio=100   filter="true"               -> FAILED err=87
OPEN    NETWORK prio=0    filter="true"               -> OK
OPEN    SOCKET prio=0     filter="event == CONNECT"   -> FAILED err=87
same priority, overlapping NETWORK filters (x2)       -> OK
```

Conclusion: priority was never the cause; the layer itself is unavailable on this build.

All five verified by rebuild from the moved tree (`Desktop\Flowbit-Source`) plus
appmon (55) / applimit (55) / ui (63) / diagnostics (32) suites — 0 failures.
